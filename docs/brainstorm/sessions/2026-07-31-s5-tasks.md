## The finding: the board the founder described already exists, exactly as described

The founder's first half was *"tasks assigned from the dashboard land on a particular board,
configured so each teacher sees only their own and the admin sees all."*

That is shipped, and it is shipped with the semantics named:

| Asked for | Status |
|---|---|
| One board for rail-assigned tasks | ✅ **Follow-ups**, `ensure_followups_board` (`services/insights/actions.py:51`), in the seed |
| Teacher sees only her own rows | ✅ `task_scope='assigned'` (`models/board.py:31`), enforced server-side (`task.py:265,275`) |
| Admin sees all | ✅ `can_view_all_tasks` (`core/visibility.py:67`) |
| Teacher is told | ✅ instant notification on assignment (`task.py:491`) |
| Admin can check it got done | ✅ `/dashboard/tasks` — open/overdue/completed **by assignee**, red rows named, *Reassign · Extend · Nudge* |

It is also **public with scoped rows rather than private**, and the reason is written in the code:
law 5 says an admin does not see private boards they aren't a member of, so a private per-teacher
board would be one the admin could fire tasks into and then never track. *"Make it private"* is the
obvious instinct and it is the wrong one. `D-40` records the existing design rather than changing
it.

**And one thing is built and merely unreachable** — the pattern from sessions 2, 3 and 4 holding
for a fourth time. `HomeService.my_tasks` (`services/home.py:117`) already returns every task
assigned to the caller across all boards, board name included, sorted overdue → soonest → undated,
with today's completions so a ticked row renders struck-through. That is the founder's My Day list,
already computed, rendered only on `/tasks`. Most of `D-41` is a frontend packet.

So, as in every session since the second, the useful conversation was **what is wrong with it**.

## 🔴 Five verified defects

**1 · The board is a ledger, not a list — and the open rows are the worse half.**
`board_table` (`task.py:267-271`) returns every non-cancelled instance on the board: no window, no
limit, oldest first. ~450 rows by day 90. The founder anticipated this for *completed* tasks; a
done row is at least a true statement about the past. What kills the board is the **open** rows
nobody closed — a *"Call Kabir Shah's parent"* from March above today's work. Once a teacher stops
reading the board, the admin's entire assign-and-check loop is dead, and no dashboard reports that.

**2 · The admin's Today tab hides the tasks the admin assigned.**
`web/src/app/(app)/tasks/page.tsx:156` re-filters board rows on the client:

```ts
rows = (boardTable.data?.rows ?? []).filter((r) => !r.assignee || r.assignee.id === myId)
```

The server computed visibility correctly and the client discards it. An admin opening the
Follow-ups tab sees **nothing they handed out** — they must know to go to `/boards/[id]`. Two
implementations of one rule; ux-principles §9 in a single line.

**3 · Every rail follow-up is due at 05:30 in the morning.**
`_assign_followup` defaults `due_at` to midnight **UTC** (`actions.py:231`) — 05:30 IST — stored
verbatim with `all_day=False` (`task.py:471`). A follow-up assigned Monday is **already overdue
when the teacher opens My Day on Tuesday**, with a time nobody chose. Every other date in this
product goes through org-local day bounds.

**4 · Three days of absence make three identical tasks.**
The rail's idempotence key is *(kind, subject)* **for today only** (`done_today`,
`actions.py:92-109`). That is exactly right for *"don't message this parent three times this
morning"* — the thing it was built for. It is wrong for a task: on day two the same student
produces a second *"Call Kabir Shah's parent"* while the first is still open.

**5 · The task doesn't know who it's about, so the outcome has nowhere to go.**
`followup_actions.detail` carries the `task_id` (`actions.py:235`) but the link is one-way — the
`TaskInstance` is a title string. So the teacher can't tap through to the student, the student's
timeline never shows a follow-up was raised, and when Kabir walks back in on Wednesday nothing
closes it. We record the **press** and never the **outcome** (ux-principles §8) — which is also
why defect 1 accumulates.

## The one real design argument

`D-41` puts a block **on** My Day. `D-24` (session 3) kept the timesheet off it — *"nothing else
goes in it"* — and `D-36` (session 4) took the homework block off it. Three sessions, three
different answers, unless there is a rule.

There is:

> **If the work happens on another screen, put a counted button on My Day.
> If the work *is* the row, put the row on My Day.**

Homework's work is a forty-name check sheet — the block was a shortcut to a screen, so a counted
button lost nothing. A task's whole work is one checkbox; the row *is* the destination, and sending
a teacher to `/tasks` to tick it adds a navigation for zero information. `D-24`'s load-bearing
clause survives untouched: **nothing goes above the periods.**

Written into `decisions.md` under `D-41` so session eight doesn't delete the section citing `D-24`
— and with the corollary that if tasks ever grow subtasks or a required note, the test flips and
they become a counted button too.

## The archive question, answered

`Q-45` was the founder's. The recommendation is **neither archive nor nothing**: window the read
(`S-103`). Open rows always, done rows from the last 7 days, everything older behind a date filter
on the same board. No migration, no nightly job, nothing moved — and it is the discipline
`my_tasks` already uses. Archiving invents a state meaning "old", needs a job, and creates a second
place a task can be.

**One condition decides whether it works:** the date filter ships *with* the window, never after
it. A window with no way to look back is data loss from the user's side.

And the harder half gets `S-104`: a **Stale** group for untouched open rows, with two actions —
close it, or give it a new date. **Never auto-close.** Silently closing *"Call Kabir Shah's
parent"* asserts that a child's parent did not need calling, and writes "handled" into an
append-only history when nobody handled it.

## Second pass — the founder narrows My Day, and the session closes

The four questions went back to the founder and came back answered in one move.

> *"Let's not put all the overdues and all pending tasks — only recently assigned, up to 3 days,
> and any tasks needed to complete today. Less clutter, because we have a home page in the task
> module where we can show all the tasks."*

That is **`D-43`**, and it is a better rule than either version designed an hour earlier. It
answers `Q-46` and `Q-47` together by narrowing the **contents** instead of capping the count or
picking a board — the filter is by **rule**, not by author or board:

- rail-assigned **within 3 days**, ∪
- **due today**, from any board.

Three consequences worth recording:

1. **The *Upcoming* dropdown from `D-42` is gone.** A future-dated task is neither due today nor,
   past three days, recent — it is exactly what *"we have a home page for all the tasks"* means.
2. **`S-108` survives as a state, not a group.** There is no backlog on My Day to group any more,
   but a row *inside* the window that is late still reads *"due yesterday"*, in red. Late is a fact
   about the row; it is not a place.
3. **`/tasks` gains a job it did not have.** It is now the *only* place her overdue, future and
   undated work exists. It has to be complete, because nothing else is.

**The one risk this creates, and the line that answers it:** a task can leave My Day **without
being done** — on day four a rail follow-up drops off whether or not it was closed. That is the
decluttering working as intended, and a silent memory hole unless the section admits it. So the
section ends with **`4 older tasks →`**. Identical discipline to `D-44`'s date filter: *a window
with no way to see past it is data loss from the user's side.*

It also raises the stakes on `D-45`. With My Day forgetting a follow-up after three days, the Stale
group on the admin's board is no longer housekeeping — it is the **only** mechanism that stops a
dropped follow-up staying dropped.

Everything else was accepted as proposed: `S-103`→`D-44`, `S-104`→`D-45`, `S-105`→`D-46`,
`S-107`→`D-47`, `S-106`/`S-111`/`S-112`→`D-48`.

**One detail deliberately left to build time:** count the 3 days in **working days**. Calendar days
make a Friday follow-up invisible on Monday — which is, precisely, the bug session 4 found in the
homework queue. Noted in `D-43` rather than raised as a question.
