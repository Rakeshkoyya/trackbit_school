## The finding: capture is built; **organisation** is not

SC-5 shipped the exam-first capture flow on 2026-07-12. Against the brief:

| Asked for | Status |
|---|---|
| Multiple exam types recorded in one place | ✅ nine types on `assessment_cycles.type` — **but a fixed list, see below** |
| A page where the teacher enters marks | ✅ `/students/scores/[classId]`, Whole class \| Few students |
| Photo scan → extract names + scores | ✅ AI transcribes, `score_match.py` **decides** identity — roll → exact → fuzzy → unmatched-with-candidates |
| Extract the paper's basic details | ✅ `parsed_meta` prefills title / subject / total / topic / date |
| A report for a student | ✅ `growth.py` → `/students/[id]` |
| Class / subject / school analytics | ✅ `class_analysis`, `insights/exams.py`, `/dashboard/exams` |
| **Evaluate whether the paper is done correctly** | 🔴 **not built — the one genuinely new ask** |

So the useful conversation, for the fifth session running, was **what is wrong with it** — and here
the answer is unusually coherent: the module **records** exams faithfully and **organises** them not
at all, which is exactly the word the founder used.

**One thing already right, and it is what makes the new ask decidable:** the AI split. The model
**transcribes** (*"Transcribe what is printed — never invent"*, `ai/scores.py:30`), deterministic
code **decides** (`score_match.py` refuses to attach a `student_id` the roster doesn't confirm, and
never lets one student be claimed twice). Nothing in the module currently asks a model for an
opinion.

## 🔴 Five verified defects

**1 · A school that runs "CET" cannot record a CET.**
`assessment_cycles.type` is a **CHECK constraint over 9 values** (`models/assessments.py:57,84`).
The founder named CET; it isn't one. The school files it as `class_test` and no analytic can ever
separate it again.

**Three weeks ago the identical question was answered the other way, with the reasoning written
down.** `core/work_types.py`: *"the column is plain Text with **no CHECK constraint**: a school that
renames its work must never lose rows to a database error… an unknown value titles itself instead of
vanishing."* Two modules, opposite answers — and the exam one is where the staffroom's own
vocabulary matters most.

**2 · Every kind of test pools into one average.**
`ExamInsights.board` computes `tot_s / tot_x` across all cycles; `by_subject` pools raw marks
(`insights/exams.py:126-164`). A 5-mark slip test and an 80-mark term exam are added into one
fraction. A `type_filter` exists and **defaults to none**, so the first number the admin reads is
the blended one. *"Maths is at 61%"* is the mean of an April diagnostic, twelve slip tests and one
final — a fact about nothing.

**3 · A student's report card cannot tell a slip test from the finals.**
`GrowthScore` is `{cycle_name, date, score, max_score}` — **no type** (`schemas/growth.py:55`). One
series is drawn through all of them. A child at 40% on slip tests and 85% on finals reads as
*erratic*; a child flat at 60% across both reads the same as one flat at 60% on slip tests alone.
This is the screen a class teacher sits in front of a parent with.

**4 · The planned exam and the marked exam are two unrelated objects.**
V2-P7's `exam_portions` ties a `calendar_events` **exam block** to a class-subject and the topic the
portion runs to (`models/exams.py`). **`assessment_cycles` has no `exam_event_id`.** So the planner
knows what an exam will cover, the results know what was scored, and **nothing can ask "we covered
70% of the portion — what did it cost?"** That question is the reason to have both modules, and it
is one nullable column away.

**5 · An exam saved through the new flow can never show as verified.**
`ExamService.save` writes `entered_by` only (`services/exams.py:275`), while the feed renders
*"· verified"* off `bool_or(verified_by IS NOT NULL)`. A badge on screen with nothing behind it.
Either verification means something here and gets a surface, or the badge goes.

## The new ask, and where the line is

> *"we also evaluate if the exam paper is done correctly or not (this is optional)"*

**This is a different kind of AI claim from anything else in the product.** Every existing call
either transcribes, or proposes a mapping a deterministic validator then checks against real data —
`ingest.py` filters the model's column guesses against the actual column list; `score_match.py`
checks names against the actual roster. **There is no roster to check "is this answer right"
against.** It is the model's opinion, about a child, with nothing behind it — and stored once, it is
one join from a report card and two from a parent.

That is an argument for **scoping** it, not for refusing it. `S-116`: ship the half that has a
ground truth — a **marking check**, two claims, both about the **teacher's paper** rather than the
child's mind:

- **the marks don't add up** — per-question marks sum to 23, the header says 25;
- **a question looks unmarked** — no tick, no cross, no number beside it.

Both are checkable by the school in three seconds, neither needs the model to know the subject, and
a mis-totalled paper is the most common real error in a marked stack *and* the one that reaches a
parent. `S-117`: anything judging the answer itself stays behind a flag, is shown only while a human
has the paper open, is phrased *"Q4 may need a second look"* rather than as a verdict, and is
**never persisted**.

**Fence note (`Q-51`):** SPRD2 §11 fences *test authoring/conducting*. Evaluation is neither, so the
letter does not block this — which is precisely why it should be decided out loud instead of
arriving by drift.

## The trap this module walks toward, named before anyone builds it

The natural next thought after *"organise the exams"* is **weights** — slip test 10%, term exam 60%,
one composite number per student. **That is the report-card designer SPRD2 §11 fences, and the fence
is right:** every school wants different weights, the composite is checkable against nothing, and
within a term the argument about the weights becomes the product.

`S-114` gets the same honesty for one nullable column: **`scale` = `minor` | `major`**. Trajectory is
drawn from **minor** (frequent tests are what show movement); standing is read from **major**; the
two are **never added**. It fixes defects 2 and 3 together, and it has no policy in it to argue
about.

## What Claude pushed that wasn't asked for

- **`S-113`** — the type is the school's own word. Copy `work_types`, drop the constraint.
- **`S-114`** — `scale`, and never pool across it. The founder's "organise them" in one field.
- **`S-115`** — one nullable `exam_event_id`, and the syllabus↔results join finally exists.
- **`S-118`** — the student's average needs its denominator too. *"61% across 5 of the 9 tests 8-B
  sat"*. `insights/exams.py` already refuses a bare average at school level; the child's card has no
  equivalent, so a student absent for the hard ones reads as strong.
- **`S-119`** — put the paper on the child's page. The photos are kept forever as evidence (P5) and
  rendered on the exam screen, but `/students/[id]` shows a number with no way back. *"Can I see
  it?"* is the one question a parent meeting produces, and it is unanswerable on the screen where it
  is asked. `storage.url_for` already exists; it is a link.
- **`S-120`** — per-question capture for objective tests is a **different module**. For an MCQ paper
  the analytic that matters is *"nineteen of thirty got Q7 wrong"*, which points straight back at a
  topic — genuinely valuable, and the only idea in this session needing a new table. Named so it
  doesn't arrive quietly as "one more field".

## Second pass — verify-and-lock, and the training corpus

The founder came back with two things: the exam type (answering `Q-49`) and a new one.

> *"once the scan is done teacher will verify it and lock the data, so internally we can capture the
> data of images and the validation data for that image so later on we can train our own model —
> but this idea is for future."*

### The exam type — `D-55` improves on session 6's proposal

Session 6 recommended dropping the CHECK constraint on `type`. The founder's answer — **a new
column beside it** — is better, and for a reason the session missed: **code branches on `type`**
(`diagnostic` routes to the skill grid, `band_test` is admin-only, `grid_only` in the feed). Free
text there would put the school's vocabulary and the system's control flow in one field. Splitting
them is right: **`type` = the system kind, read only by code; the new field = the school's word,
the only one any screen shows or groups by.**

`S-135` argues the new field should point at a small **`exam_types` table** rather than being free
text, because it is *the grouping key for a year of trend lines* — *"CET"*, *"C.E.T"* and *"Cet"*
typed on three evenings become three series on the admin's chart. `work_types` gets away with free
text because a timesheet bucket is never a chart's x-axis. The table also carries `scale`
(`S-114`), so the school configures *"CET = minor"* once and the teacher picks one thing per exam
instead of two. Precedent: `board_categories`.

### 🔴 The lock is what makes the corpus valid — this is the finding

*(verified)* `ExamService.save` **full-deletes and re-inserts** a cycle's scores on every edit
(`exams.py:270-279`). Two of the three things `D-54` needs are already stored and already survive —
the images (`score_capture_pages`, forever, P5) and the model's read (`parsed_rows` +
`parsed_meta`, cleared only by re-uploading a page, `score_capture.py:167`).

**The third — the human's answer — exists only by inference, and the inference decays.** The
corrected marks live in `assessment_scores`, a different table with a different lifecycle, rewritten
in full whenever anyone edits the exam. So a mark corrected in November silently replaces the mark
confirmed in July, with no record they ever differed.

For a report card that is survivable. For a training corpus it is fatal: **the label half of every
pair keeps changing after the fact**, and a dataset with drifting labels is worse than no dataset,
because nothing tells you which rows moved. `D-53`'s lock is what freezes it — and it also finally
gives `assessment_scores.verified_by` the meaning session 6 filed as defect §4.5 with no owner.

**Two notions of "confirmed" already exist and neither did this job:**
`score_captures.confirmed_at` **is** set (the photos were reviewed);
`assessment_scores.verified_by` is **never** set by this flow, which is why the feed's *"· verified"*
badge cannot light up. `D-53` picks the second, because that is the one the analytics read.

### What Claude pushed on the corpus

- **`S-137` — store the diff, not both sides.** The value is concentrated almost entirely in rows
  the human changed. Fifty thousand correctly-read pages teach very little; *"a 7 read as 1"* is the
  whole dataset. Written once, at lock.
- **`S-140` — record *why*, in four buckets** (`misread_digit` · `wrong_student` · `unmatched` ·
  `header_wrong`). One tap on the review row, and the corpus becomes queryable as *"the model
  confuses 7 and 1 in this handwriting"* rather than *"these two rows differ"*.
- **`S-138` — ask for it.** This is **the first data in the product whose purpose is not running the
  school**. Every other byte serves the school that entered it; this serves us, and it is children's
  handwriting with their names on it. An org setting, default off, agreed at onboarding — the shape
  already exists on `organizations`.
  ⚠️ **De-identification cannot happen at capture** — the matcher needs the name to verify the row,
  and the child's name is on the image in their own hand. The corpus is PII until it is cropped or
  redacted **on the way out**, so that step must exist before the first *export*, not the first row.
- **`S-139` — unlocking is an appended row with a reason**, never a mutation (law 3), and it
  **flags** the affected pair rather than rewriting it. `plan_approvals` / `demo_request_notes` /
  `leave_request_events` are all this shape already.
- **`S-141` — the storage number, said once:** ≈ **20 GB per school per year**, kept forever. Cheap,
  fine, and better as a decision now than a surprise in month nine. It also argues for keeping the
  **page** image we already store rather than per-student crops, which would cross the
  batch-evidence fence (P5).
